# Changelog

All notable changes to TTGO are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed
- **The AI features switch now stops test generation on the server too.** With AI switched off, `POST /api/ai-generations`, draft regeneration and the legacy `POST /api/requirements/{id}/generate-tests` answered and called the LLM as usual; only the UI hid them. They now answer 409 `{"error":"AI features are switched off"}`, like failure analysis. Import is not an AI feature: `POST /api/import/parse` still runs its deterministic parsers, and only the LLM fallback is skipped (the same 422 as when no provider is configured, ending "AI features are switched off"). The LLM and TypeSafe.ai connection tests and the prompt preview stay available, so admins can configure providers before switching AI on.
- **A Jira or Confluence token that can't be decrypted no longer locks the settings or goes out as ciphertext.** When `secret.key` is lost or rotated, or the database is restored or copied from another instance, a stored token no longer decrypts. The settings now load anyway and report `api_token_status` (`missing`, `ok` or `undecryptable`); the token can be re-entered or removed (`clear_api_token`), and saving the other fields keeps the stored token untouched. Calls that need it answer 422 "the stored key can't be decrypted — re-enter it" instead of sending the ciphertext to Jira or Confluence. A token that cannot be encrypted is no longer stored in plaintext: the save is refused with a 500 that says why.
- **An LLM provider key that can't be decrypted is reported, not sent.** Provider rows report `api_key_status` (`missing`, `ok` or `undecryptable`) and the list always loads; the key can be re-entered or removed (`clear_api_key`), and model, default, enabled and delete keep working without touching the stored key. Nothing is sent to the provider without its key: the connection test answers 422, a generation fails with category `configuration` (422, also on replay), the import's AI fallback reports `category: configuration`, and failure analysis records each attempt as failed with `error_category=configuration` (or leaves the LLM out when TypeSafe.ai decides). Keys are no longer stored in plaintext when encryption fails, and the demo dataset's provider key is stored encrypted. Settings shows it: a provider row gets a red "Key unreadable" pill, and the provider dialog and the Jira and Confluence settings say "Stored key/token cannot be decrypted — enter it again" and offer to remove it.
- **Disabled buttons now look disabled.** Primary and secondary buttons (`.primary-btn`, `.action-btn`) had no disabled style, so a button that could not be clicked yet (Create in the New Defect dialog before a title is typed, Save changes on Settings → AI while a setting is invalid) looked exactly like an active one and still lifted and brightened on hover. Disabled buttons are now dimmed with a not-allowed cursor and no hover effect, in both themes. The per-button workarounds that dimmed a few of them inline were removed; two of them (the New Defect and Edit Defect dialogs) even forced full opacity while the button was disabled for an empty title.
- **Run completion queues automatic failure analysis for a TypeSafe.ai-only setup.** Completing a run queued the automatic analysis only when the default LLM provider was approved for "Auto failure analysis", even when TypeSafe.ai, allowed on automatic analysis, could decide alone, so a setup without an approved LLM was never analyzed on completion. Completion now asks the same resolver the analysis worker uses and queues whenever it can analyze automatically: TypeSafe.ai with "Allow on automatic analysis", or an approved default LLM. With TypeSafe selected but no usable key the run is still queued, so each group takes the "TypeSafe unavailable" path (the LLM fallback, or a failed attempt that names the missing key), as an analysis started by hand does.
- **The AI features switch no longer claims automatic failure analysis keeps running while it is off.** The server has refused new analyses and stopped queueing completed runs while AI is off for some time; the note under the switch now says so.
- **Clearing "Max analyses per run" or "Groups analyzed at once" no longer saves as 0.** The AI Failure Analysis card sent an emptied number as 0, which the server rejects with a 400. The card now flags the field in red and keeps Save disabled until the cap is a whole number from 1 to 500, groups at once from 1 to 8, and the prompt is not empty.
- **AI failure analysis of an older run no longer sees what happened after it.** The history block (this test's recent failures and the defect types people gave them) covered the 30 days before *now*, excluding only the analyzed run, so analyzing or explaining a failure from an earlier run also showed the model failures from later runs, with their triage labels: evidence nobody had when the failure happened. The window now ends at the analyzed result's own start time (or, for a result recorded without timing, when it was recorded), and only failures strictly before it are listed, compared as instants so a result recorded in UTC next to server-local times falls on the right side; the 30-day lookback and the five-entry limit are unchanged. Analyses of the newest run, including the AI engine benchmark's, were not affected.
- **Failure analysis now redacts every field it sends out.** Redaction covered the error message, stack, log and history messages, but the test name, categories, environment, browser, OS, app version, steps, linked defect and requirement titles, and the test name and failure type in TypeSafe's semantic-grouping excerpt went to TypeSafe.ai and the LLM as stored. With redaction on (the default), all of them now pass through the same filter.
- **Failure analysis no longer records a cut-off LLM reply as an "unknown" verdict.** Failure-analysis LLM calls, both the verdict call and the explanation written for a TypeSafe decision, were capped at 1,024 tokens. A verbose model such as deepseek-v4.1-flash could hit the cap on the first call and on the repair retry, and the incomplete JSON was stored as verdict unknown with no suggestion, which the run page, the accuracy ladder and `ttgo ai compare` all read as the model declining to answer. The cap is now 2,048 tokens. A reply that stops at the cap is retried with a request to keep every field brief. A reply cut off twice is recorded as a failed call (no model name, summary "analysis failed: llm call: LLM reply cut off at the length limit twice"); for an explanation, or for an LLM taking over from TypeSafe, TypeSafe's decision is kept and the card says the reply was truncated. A failed call keeps the tokens both attempts consumed, so its cost stays visible. On the AI benchmark, deepseek completed all six replies it had previously lost this way. A higher cap was tried and rejected: at 4,096 tokens a slow model outlasts the default 90-second provider timeout.
- **Opening a test case no longer loads its side panels twice.** The Latest Executions list, the Activity timeline and the Reqs / Linked Defects tab counts each flashed back to a loading state a moment after they had already rendered. Both loaders resolved the test id as `test?.id || testId` but listed each source separately in their dependency arrays, so when the fetched test arrived and `test?.id` caught up to the route parameter the effect saw a dependency change and re-ran with the very same id — a second, redundant round trip per panel. The version/requirement/defect loader also cleared its state at the start of that second run, which is why the Activity timeline and those two tab counts blanked out and repopulated. Both effects now depend on a single derived id, and each retires its own response if a newer one supersedes it, so switching between test cases quickly can no longer land an older response over a newer one.
- **Category pickers and filters now list every category, not just the first ten.** The test grid, the run list and the test-case detail panel each requested categories without paging arguments and so took the endpoint's default page size, silently hiding every category past the tenth from selection and filtering on any instance with more than ten. All category pickers now read one shared, unpaginated copy of the list, which also removes the duplicate requests those independent fetches produced — opening a test case issued six identical category requests where the app now makes one in total, refreshed when categories are created or deleted. The Category Management screen keeps its own paginated fetch, since it needs page and search parameters.
- **Comment, version-history and linked-requirement panels no longer risk showing another record's data.** All three are reused in place when the surrounding detail view switches records, and their fetches had no way to retire a superseded response, so an older request resolving last would overwrite the current one. Comments and version history are additionally refetched imperatively — after adding, editing or deleting a comment, and on history retry or restore — which could race the same panel's own reload. Each now discards responses that a newer request has superseded.
- **Concurrent result writes for the same test case no longer fail with a 500.** `POST /api/runs/{id}/results` picked the next `attempt_number` with an unsynchronized read-then-insert, so parallel writers read the same `MAX(attempt_number)` and all but one lost the UNIQUE index race — surfacing as an opaque `{"error":"internal server error"}` with no hint that a retry would succeed. This is exactly the documented CI path: parallel shards and automatic retries reporting one test case at once (measured on a live instance: 12 concurrent writes → 7 created, 5 failed). The read and the insert now share one transaction that opens with the parent run's `updated_at` bump, so it takes SQLite's write lock from its first statement and concurrent callers queue on `_busy_timeout` instead of deadlocking on a read-to-write upgrade, which SQLite rejects immediately regardless of that timeout. That leading write's `RowsAffected` also replaces the separate parent-run existence check, closing the window where a run deleted mid-call left an orphan result. Covered by a regression test firing 12 simultaneous writes and asserting attempts land as 1..12 with no gaps or duplicates (file-backed, since `:memory:` gives every pooled connection its own database and could never contend).
- **`GET /api/settings/confluence` no longer 404s when the integration is simply not configured.** Pages probing integration availability (Requirements — mounted alongside Analytics under Quality) logged a red 404 in the browser console on every fresh install, because "not configured yet" was reported as an error while the equivalent Jira endpoint already answered `200 {"enabled": false}`. Confluence now mirrors the Jira shape; the Jira handler's stale doc comment (still describing the old 404 behavior) is corrected too. No functional change for configured installs.
- **`GET /api/runs/{id}/analysis-job` no longer 404s when the run simply has not been AI-analyzed.** The run-detail page mounts a progress banner that polls this endpoint on every open, so any run that had never been through failure analysis — the overwhelming majority, including every run on the public demo stand — logged a red 404 in the browser console, which reads as a broken feature while nothing is actually wrong. Worse, the handler never checked the run at all, so a genuinely bad run id and a valid run with no job yet returned the identical 404 and the status code could not tell "wrong URL" from "nothing yet". The endpoint now verifies the run exists and 404s only for a missing run, returning `200 null` when there is no job — matching `GET /api/runs/{id}/analyses/current`, which already answers `200 {}` for the same empty case. The banner needs no change: it already treated a missing job as "render nothing".
- **"Latest Executions" on a test case now orders by when the execution ran, not when its row was last written.** The panel sorted on `updated_at`, which drifts from execution time in both directions: any later edit (a triage decision, a screenshot upload) bubbled an old execution to the top, and seeded history — written newest-run-first — came out fully inverted, oldest day on top. The query now orders by `start_time`, falling back to `updated_at` only for results recorded without timing so a freshly added manual result still surfaces sensibly. The AI demo generator also stamps each seeded result's `created_at`/`updated_at` with its execution end time instead of the insert moment, so every timestamp-ordered view treats demo history like organically recorded data.

### Added
- **Failure-analysis cost is tracked.** Every billable failure-analysis call (TypeSafe decisions, LLM decisions and explanations, later Explain requests, semantic grouping) is recorded with the prices in force when it was made, in a new `ai_analysis_cost_events` ledger. TypeSafe.ai settings gain a price per million input tokens (default 0.042). This month's spend against the monthly AI budget now includes failure analysis, and the budget card and `GET /settings/ai-budgets` split it into test generation and failure analysis. The Analytics AI section and `GET /ai-generations/reports/summary` report failure-analysis cost for the same window (TypeSafe vs LLM, and the part spent on explanations). Analyses from before this release have no cost records.
- **Failure analysis respects the soft AI budgets.** Analyze, Analyze failures, Retry failed groups and Explain now estimate their cost (the prompt bound plus the reply cap at the provider's prices, and TypeSafe's state bound at its price per million tokens) and ask for confirmation when the per-request budget or the rest of the monthly budget would be exceeded; the API takes `acknowledge_budget=true` as a query parameter. Automatic analysis on run completion is skipped instead when this month's spend plus the run's estimate would exceed the monthly budget: the run page says so, with the amounts, and offers **Run anyway**. A started job always runs to the end.
- **Analysis job timing and rate limits.** The run's analysis summary shows how long TypeSafe decisions and LLM calls took (average, median, slowest) and how many rate-limit responses the job hit, retried ones included; `GET /runs/{id}/analysis-job(s)` returns them as `decision_ms_*`, `llm_ms_*` and `rate_limit_hits`.
- **Outbound TypeSafe.ai calls share one rate limit.** Every TypeSafe.ai request the server makes (failure-analysis jobs, a single Analyze, semantic grouping and the settings connection test) now draws from one process-wide token bucket, 1000 requests a minute by default (`TYPESAFE_RPM` overrides it; `0` turns it off). A call waits for its turn instead of failing, each retry takes its own turn, and a cancelled job stops waiting at once. Before, parallel groups and concurrent jobs each paced themselves only through TypeSafe's own 429 replies.
- **Settings → AI Generation shows how failure analysis will run.** A new AI Failure Analysis section puts the TypeSafe.ai and AI Failure Analysis cards under a diagram of the six steps an analysis takes (start, grouping, evidence, verdict, explanation, storage) for an analysis started by hand or by run completion. It redraws from the cards' unsaved edits; marks what a setting skips, blocks or puts at risk; tags each step that sends failure text to TypeSafe.ai or the LLM (amber when redaction is off); and every setting it names jumps to that setting. The rules are a port of the server's resolver and analyzer, so it follows each TypeSafe outcome (kept, taken over by the LLM, fallback, failed attempt) with its own explanation, and says so when it cannot know something, such as whether a newly typed key works. Every failure-analysis setting also gains a "What this does" explanation with a worked example. The diagram replaces the TypeSafe.ai card's "What an analysis will do" panel.
- **A run's failure analysis works on several failure groups at once.** A job used to analyze its groups one after another, so its time was the sum of every TypeSafe.ai and LLM call: on the AI benchmark run, 147 s for minimax on 24 groups and 78.5 s with Jev deciding and minimax taking over 10 of them, nearly all of it waiting on the LLM. Settings → AI Failure Analysis gains "Groups analyzed at once" (`parallel_groups`, 1 to 8, default 4): that many groups are analyzed concurrently, each still under its own five-minute deadline, while every result is written by a single goroutine in the order it finishes. Cancelling stops new groups from starting and abandons the ones in flight; a server that stops mid-job leaves the job to the restart sweep rather than marking it completed. Measured on the benchmark run with four at a time: Jev with minimax taking over below 90% went from 78.5 s to 31.7 s, and minimax alone from 147 s to 69 s, where the slowest few calls (up to 29 s) now set the pace. Lower the setting if the LLM provider answers with rate-limit errors. `PUT /api/settings/ai-failure-analysis` accepts `parallel_groups`; leaving it out keeps the stored value.
- **Failure analysis says which route it will take, and a TypeSafe-only route sends nothing to the LLM.** The TypeSafe.ai card gains "Use the default LLM when TypeSafe is unavailable" (`llm_fallback_enabled`, on by default) and a summary of what a manual and an automatic analysis will do with the settings on screen: who decides, who explains, what happens below the takeover threshold and when TypeSafe is down, and whether any failure data reaches the LLM. With explanations, takeover and fallback all off, no LLM is attached to the job at all, so a missing, disabled or misconfigured LLM provider no longer blocks it, and an automatic run needs only TypeSafe's own consent. With the fallback off, a TypeSafe outage is recorded as a failed attempt instead of quietly handing the failure to the LLM; a missing or undecryptable TypeSafe key counts as an outage (`error_category: "configuration"`), so it cannot turn a TypeSafe-only setup into an LLM route. The AI master switch now stops failure analysis on the server too (sync analyze, job enqueue, retry and Explain answer 409, automatic analysis on run completion is not queued, and a queued job fails with "AI features are switched off"), and the per-provider consent for automatic analysis is read when the job runs rather than when it was queued.
- **A failed analysis attempt is recorded as failed, not as an "unknown" verdict.** Analyses carry `decision_status` (`ok` or `failed`) and an `error_category` (`timeout`, `rate_limit`, `provider`, `truncated`, `unparseable`, …); `unknown` is now only ever a real answer. A failed attempt keeps the engine, model and tokens it spent, a single Analyze that fails is stored in the version history and returned with a 502 (`{"error", "analysis"}`), and existing rows that were failures in disguise are marked on upgrade. The analysis card shows the failure and its cause, the verdict badge reads "Analysis failed". Each LLM call is retried once on a transient error, each failure group has a five-minute deadline (reached after TypeSafe has decided, it keeps the decision and marks the takeover or explanation unavailable), and cancelling a job now abandons the request in flight instead of waiting for it. Analyses record how long the decision and the LLM calls took, how many calls were made and why the last reply ended (`decision_ms`, `llm_ms`, `llm_calls`, `finish_reason`).
- **The run banner reports how a finished analysis went and can retry what failed.** After a job ends, the banner shows the groups decided, failed, unknown, taken over by the LLM and left without an explanation, and the pipeline the job ran; a job with failures offers **Retry failed groups**, which queues a job limited to the results whose current analysis failed (`POST /api/runs/{id}/analysis-job/retry-failed`, 409 when nothing failed). `GET /api/runs/{id}/analysis-job` includes the `outcomes` counts. A clean finish is shown only to the page that watched it run; anything needing attention stays until dismissed.
- **Explain a TypeSafe decision on demand.** A TypeSafe analysis stored without an explanation (explanations off, or the explanation call failed) shows one compact notice with an **Explain** (or **Retry explanation**) button instead of empty Summary and Next-action boxes. The button asks the default LLM for the explanation and stores it on the same analysis: the verdict, confidence and suggestion do not change and no new version is created (`POST /api/run-results/{id}/analyses/{analysisId}/explain`). Explaining an older version leaves the run grid on the newest one.
- **Every analysis names the job and pipeline that produced it.** Analyses carry `job_id`, and a job records the pipeline it ran (decider and question-set version, narrator, explanations on or off, takeover threshold, fallback, reply cap) with a readable label such as "TypeSafe jev-1.13, decisions only, minimax below 90%". An LLM takeover also records TypeSafe's own verdict, confidence and suggestion (`takeover_from_*`), shown on the analysis card. `GET /api/runs/{id}/analysis-jobs` lists a run's jobs with their pipelines and outcomes, and `ttgo ai compare` gains `--job <id>` (one job's analyses) and `--by-job` (one column per job, labelled by pipeline), so two passes with the same model but different settings no longer merge into one column; failed attempts show as FAILED cells and are counted, not graded.
- **The LLM can take over when TypeSafe.ai is unsure.** The TypeSafe.ai card gains "Ask the LLM when TypeSafe's confidence is below (%)" (`escalate_below_pct`, 0 to 100, default 0 = never). When TypeSafe's verdict confidence is under the threshold, the default LLM provider decides and explains the failure in one call, exactly as the generative pipeline would; the analysis is stored and graded as the LLM's, its rationale opens with TypeSafe's verdict and confidence, and it carries TypeSafe's input tokens as well. If the LLM call fails, or its reply cannot be read, TypeSafe's decision is kept, with the tokens the LLM consumed. Replayed on the benchmark data with minimax-m3 as the LLM, a 90% threshold sent 10 of 24 failure groups to the LLM and was right on 271 of 274 verdicts, against 252 for TypeSafe alone and 270 for the LLM alone. Run live, the combination scored 261 with minimax, 187 with gpt-5.6-luna and 184 with deepseek-v4.1-flash (after the reply-limit fix above): the LLMs changed some of their own answers between runs, and luna and deepseek both got the largest group wrong. Check the helper LLM on your own runs before relying on the threshold.
- **TypeSafe.ai decisions without an LLM explanation.** The TypeSafe.ai card gains "Write an explanation with the default LLM" (on by default). Off, a failure-analysis job stores TypeSafe's verdict, confidence and suggested defect type on their own: no explanation call, so a group is decided in well under a second, and the analysis card shows the classification with a notice and an Explain button in place of the summary (`narrative_status: "skipped"`). The LLM is still used for the takeover and the fallback when those are on (see the route entry above). `PUT /api/settings/typesafe` accepts `narrative_enabled`.
- **TypeSafe.ai calibrated verdicts and semantic failure grouping.** Settings → AI Generation gains a TypeSafe.ai card (key stored encrypted and masked, pinned model `jev-1.13.0`, per-feature switches, a separate consent for automatic analyses, and a connection test). When enabled, TypeSafe's System One model decides each failing result's verdict and suggested defect type with a calibrated confidence while the configured LLM writes only the explanation; if TypeSafe is unavailable the analysis falls back to the LLM verdict and says so in the rationale. Suggestions are now stored on the analysis rather than derived from the verdict, so an `Unknown` verdict can still carry a suggestion and the suggestion may abstain. After the usual identical-signature grouping, a semantic pass asks TypeSafe which remaining failure groups share a cause and merges them (complete linkage, high-probability edges only), with the probability, model and question-set version recorded on every merged clone. The accuracy panel grades each engine separately. New API: `GET/PUT /api/settings/typesafe`, `POST /api/settings/typesafe/test`; analyses gain `engine`, `confidence_score`, `suggested_defect_type_confidence`, `narrative_status`, `dedup_method`, `dedup_p_same`. Off by default; upgrading changes nothing until an admin enters a key.
- **A heavier AI benchmark: twelve more planted failure templates and a failure-scale knob.** The AI demo dataset gains twelve templates with their own answer key — an expired service-account token, a per-environment 429 quota, an application TypeError caught from the browser console, a screenshot with a missing button, a timezone-shifted invoice date, a fixture email reused across shards, a feature flag unset in staging, a runner out of disk, an in-stock SKU missing from search, a sign-in redirect loop, an upload-progress race, and a payment gateway with its circuit open — 26 in all. `POST /api/seed/ai` accepts an optional `{"failure_scale": 1..5}` (perfseed: `-failure-scale`) that multiplies every template's dedicated cases and the newest run's incident slice, growing the catalog and run size to match, so a scale of 3 plants roughly 300 failing rows in the newest run instead of 60. A second option, `log_words` (perfseed: `-log-words`), plants a realistic timestamped log of about that many words on every failing row — step, request, wait and fixture lines with occasional warnings, the failure line last — so the engines can be benchmarked with logs of the size real suites produce instead of the three-line tail. The default dataset is unchanged. Reloading at a different scale replaces the previous copy; Remove Demo Data clears any rows a larger copy left behind.
- **`ttgo ai compare <run-id>` puts the AI engines side by side.** The CLI pivots every stored analysis of a run's failing results by engine and model (TypeSafe and each generative LLM get a column, latest version each), marks the rows where they disagree, and summarizes per column: verdict distribution, abstentions, mean calibrated confidence, tokens, and pairwise agreement between columns. When the run belongs to the AI demo dataset, each failure is matched to its planted template by the error message's shape and every column is graded against the answer key, overall and per confidence label. Re-analyzing a run with another engine or model simply adds a column, so the comparison needs no snapshots. The answer key comes from the new admin-only `GET /api/seed/ai` (dataset loaded, latest run id, ground truth), or from a saved copy via `--answer-key`; `-o json` prints the full pivot for scripting. Stored analyses of failed LLM calls (no model name, `unknown` at low confidence — what the analyzer records when the provider returns an error) form no column and are reported as a count instead, so a flaky provider cannot masquerade as a model's answers. Abstentions are counted by meaning, not spelling: a withheld suggestion is stored as an empty string, the question option is `insufficient_evidence`, and the answer key writes an expected abstention as the human label `to_investigate`; all three match each other in grading. Each column also reports suggestions issued versus withheld and the accuracy among issued suggestions, so an engine that abstains is not scored as if it had answered wrongly.
- **`TYPESAFE_BASE_URL` routes TypeSafe.ai calls through a gateway.** The System One endpoint is fixed to `api.typesafe.ai` unless the server is started with this variable; set it to `https://openrouter.ai/api` to reach Jev with an OpenRouter key (model `jev-1.13` or `jev-latest`). Gateways do not serve TypeSafe's model list, so the settings card's connection test now falls back to a single one-question evaluation when the list comes back empty — a wrong key is reported as a failure instead of an empty "connected". Native TypeSafe keys are unaffected.
- **AI failure-analysis demo data is loadable from Settings.** Settings → Demo Data gains an *AI Failure Analysis Demo* card that seeds the same dataset as `perfseed -profile ai` — 30 nightly runs × 500 results with planted failure groups, per-test failure history, triage labels, and linked defects — into the live database via the new admin-only `POST /api/seed/ai` (~1s). The card shows load status with an "Open latest run" shortcut, and after seeding surfaces the planted-groups **answer key** (expected verdict and defect type per template) for grading real-LLM verdicts. Reloading replaces the previous copy in place: entity IDs are deterministic, so the purge also cleanly swaps out a dataset seeded by the perfseed CLI, and any rows the app attached since (analyses, jobs, comments, triage decisions) go with it, while rows that merely reference the dataset from outside — user runs executing seeded test cases, runs under a seeded category, user subfolders — are detached the way the app's own delete flows do instead of tripping FK enforcement. Seeded entities are tracked in `demo_seeds`, so the existing "Remove Demo Data" action clears the AI dataset alongside the classic one.
- **Break-glass password recovery: a `reset-password` server subcommand, plus "Forgot password?" guidance on the sign-in screen.** Until now a sole administrator who forgot their password was hard locked out: there is no reset-email flow (by design — TTGO has no SMTP), `ADMIN_EMAIL`/`ADMIN_PASSWORD` seeding refuses to touch an instance that already has an active admin, and the `ttgo` CLI authenticates through the API — so the only way back in was hand-editing the SQLite file with a self-made bcrypt hash. The server binary now doubles as the recovery tool: `reset-password <email>` runs on the server host against the same `DB_PATH`/`.env` the server uses (shell access to the host *is* the authorization — no login involved), prints a generated temporary password, re-enables the account if it was deactivated or soft-deleted, revokes all of its sessions, and records a `user.password_reset` audit entry marked `method=break_glass_cli`. It is safe to run while the server is up (WAL journal + busy timeout) and the new password works immediately, with no restart. A mistyped email fails with the instance's administrator emails listed instead of leaving the operator guessing, and a wrong working directory reports where it looked for the database rather than silently creating an empty one. The sign-in screen documents the dead end where it happens: a "Forgot password?" expander explains the normal path (any admin, via Settings → Users → Reset Password) and, for when no admin can sign in, shows the exact break-glass command pre-filled with the typed email.
- **Self-service password change.** Settings gains an **Account** tab (visible to every signed-in user, not just admins) with a Change Password form — current password, new password, and confirmation — wired to the existing `POST /api/auth/change-password` endpoint. Until now that endpoint had no UI at all: a non-admin user's only route to a new password was asking an admin for a reset in the Users tab. The form mirrors the server's rules up front (minimum 8 characters, maximum 72 bytes, must differ from the current password, confirmation must match) and surfaces the server's verdict inline, e.g. "current password is incorrect".
- **Defects can be assigned to an owner, marked `fixed`, and updated in bulk.** `assignee_id` is now accepted on defect create, update and the create-and-link path used when filing a defect from a run result — an id assigns, `""` clears, and an absent field leaves the owner alone. The value is validated in the shared `ValidateCreate`, so every path that files a defect rejects an unknown, deactivated or deleted user with a 400 rather than storing a dangling reference, and the list and detail responses carry a resolved `assignee_name` (display name, else email) from a batch user lookup that still names an owner whose account was since deactivated. `status` gains a third stored value, `fixed`, meaning *fixed but not yet retested*; `"open"` stays fully valid and writable, so the CLI, seed data, webhooks and any external script keep working unchanged, and all four defect counters (per run result, per run, per test case, per folder) already bucketed `closed` against everything else, so a `fixed` defect counts as open with no code change. The new `POST /api/defects/bulk-update` applies one set of `status` / `severity` / `assignee_id` values across up to 500 ids in a single grouped write, tolerating ids that no longer exist and returning the updated rows fully enriched; a request that names ids but sets no field is a deliberate read-back that writes nothing, because `updated_at` is what the register reads as a staleness signal. `GET /api/defects/{id}/tests` now also reports, per affected test case, the run it **last failed** in (`last_run_id`, `last_run_name`, `last_result_status`) — the most recent `FAIL`/`ERROR` result for that test case, not merely whichever historical result the defect happened to be filed against, since a test-case-scoped link carries no result at all.

### Changed
- **A TypeSafe.ai 400 or 404 is reported as a settings problem.** A request TypeSafe.ai rejects as malformed (400) or aimed at a model or path that does not exist (404, typically a mistyped model id or base URL) was filed as a generic `internal` error; it is now `error_category: "configuration"`, like a missing key, and is still not retried. The failed-analysis card reads "Analysis failed · settings problem" and says "Check the TypeSafe.ai settings (model id, key), then Re-analyze" (or the LLM provider settings when the LLM failed), and after a job with such failures the run banner says retrying won't help until the settings are fixed; Retry failed groups stays available. Job outcomes gain `failed_configuration`.

## [0.4.0] - 2026-07-20

### Added
- **Bulk defect-type triage on a run's results.** A "Set defect type" picker in the run-results bulk bar applies one defect type across the whole selection, so working through a wave of failures is a single action instead of one dropdown per row. `status` on `POST /api/runs/{id}/results/bulk-update` is now optional to support it: a request carrying `defect_type` and no `status` is a pure triage operation — it applies only to rows whose *stored* status is a failure (`FAIL`/`ERROR`), never touches status, and returns `{updated, skipped}` so rows outside the failure set are reported back instead of being silently dropped (a selection that turns out to be all non-failures is a normal `200` with `updated: 0`, not an error). Snapshotting covers both the single-result and bulk triage paths and is best-effort — a missing or failing analysis lookup logs and clears the snapshot, never blocking a human's triage write and never scoring a new decision against a suggestion left over from an older one. A new `GET /api/ai/failure-analysis/accuracy?days=30` endpoint and an accuracy panel in AI Failure Analysis settings report the agreement rate overall, by verdict, and by confidence; the by-confidence ladder is the point — a clean descent means the model's confidence is trustworthy, a flat one means it is noise. ### Changed
- **`ERROR` results are now triageable, and their triage decisions count toward AI accuracy.** Results with status `ERROR` already received AI failure-analysis verdicts — the analyzer has always treated `FAIL` and `ERROR` alike — but the defect-type control was hidden for them and the backend forced `defect_type` back to empty on any non-`FAIL` status, so those verdicts were generated, never surfaced, and never calibrated. `ERROR` rows now show the defect-type control and the `AI: <type>` suggestion chip, can be accepted or overridden like any other failure, write the same calibration snapshot at the decision moment, and are counted in the accuracy stats. The single-result and bulk paths agree on this, so the same rows triaged either way produce the same record. Nothing is backfilled: existing `ERROR` rows keep their empty `defect_type`, still display as `to_investigate`, and stay out of the accuracy stats until genuinely triaged.
- **AI failure-analysis now grounds its verdict in context.** Each analysis enriches the LLM prompt with the failing test's own recent history (failures over the last 30 days for the same test case), its linked defects and requirements, the executed steps, and the run environment (browser / OS / app version) — plus each prior failure's human triage label (`DefectType`) and a rollup of the label distribution — instead of classifying the bare failure in isolation. It's wired into both the batch failure-analysis worker and the synchronous single-result path. Enrichment is best-effort — a failing source logs and yields an empty slot, never failing the analysis — and the enriched history is redacted alongside the primary error when redaction is on. - Default AI generation prompt fixed and aligned: the Detail Level definitions now use the exact values the UI sends ("Simplified" / "Standard" / "Detailed" — previously two of three never matched), and the coverage bullet uses the "Functional" category name from the enum. Existing installs that never customized the template are upgraded automatically on startup; customized templates are untouched (Reset to Default picks up the new text).

- Run detail's Execute button now runs only the checked results — showing the count (e.g. "Execute (3)") and scoping the execution queue to that subset. It is disabled until at least one result is checked (use the header select-all checkbox to run the whole run).

  `run` is a summary with latest-attempt counters and no `run_results`)

  deltas or re-fetch the run. Fan-out frame size is now O(changed rows)

Migrate to `/api/ai-generations`; the legacy routes will be removed in a future major release.

### Fixed
- Stored LLM/integration API keys no longer break after a `docker compose up -d` rebuild (symptom: "LLM API error (HTTP 401): Missing Authentication header", fixed only by re-entering the key). The at-rest encryption key file was created in the container's working directory (an ephemeral layer) instead of beside the database, so every container recreation generated a fresh key and made previously-encrypted secrets undecryptable. The key is now created in the database's directory — the persisted volume — so it survives rebuilds and DB restores (`TTGO_ENCRYPTION_KEY` still overrides it, and is now documented in `.env.example`/`docker-compose.yml`). One-time note: after deploying this fix, re-enter your provider keys once (the old ephemeral key is gone); they persist from then on.
- AI-generated test steps no longer display literal HTML entities (e.g. `&#39;` for an apostrophe, `&amp;` for `&`) in the AI Generate review — the compare/diff modal, step list, draft editor, and the draft-list description preview. Step text is now stored as sanitized HTML consistently (matching manually-authored and imported test cases, which are rendered via the HTML-decoding step views), and the plain-text AI-draft views decode entities for display. This replaces an earlier interim approach that unescaped step text in the backend, which was inconsistent with the other paths and could push a literal `<`/`>` from an accepted draft into the HTML-rendered run views.
- AI cost-analytics hardening (found in an independent review of the new cost features): provider prices now reject negative and non-finite values (a negative price otherwise lowered recorded spend and slipped under the budget gate); the monthly budget counts spend by when each model call actually happened (per attempt), so regenerating an older run correctly counts toward the current month; the legacy accept endpoint rejects a malformed draft-id set — duplicate, mistyped, or blank `temp_id`s mixed with real draft ids — with a 400 instead of silently creating duplicate test cases and orphaning the pending draft; and a soft-budget warning during draft regeneration can now be acknowledged in the studio ("Proceed anyway") instead of dead-ending. Concurrent regenerations of the same run no longer lose token/cost updates and a regeneration no longer reprices the run's earlier calls (usage and cost are folded with atomic per-call increments); a budget check that loses a race to a concurrent same-key request now replays the existing run instead of returning a spurious 409; and editing a draft through the legacy accept endpoint recomputes its quality and duplicate analysis instead of blanking it.
- "Erase All Data" (Settings → Demo Data) did nothing after typing `ERASE`: the confirm request omitted the body the backend requires, so `DELETE /api/admin/reset` was rejected with 400 and nothing was erased. The frontend now sends `{"confirm":"CONFIRM RESET"}`; added a backend test pinning the reset confirmation contract.
- Removed the in-place sign-in modal: anyone who needs to authenticate is now redirected to the `/login` page and returned to where they were after signing in. `/login` shows the normal sign-in form, or the first-run "Create admin account" form on a brand-new instance (no users). Previously that first-run screen was unreachable — an unauthenticated visitor only ever got the modal, which offered no way to bootstrap an admin nobody had credentials for. The `.env.example` files also no longer ship populated `ADMIN_EMAIL`/`ADMIN_PASSWORD` (copying them verbatim silently seeded an admin and skipped first-run setup), so both default to blank now.
- Logged-out visits to /login no longer fire unauthenticated app-level API calls (folder tree, LLM providers, AI features) — they 401'd noisily and popped the session-expired modal over the login form; these fetches now wait for sign-in and refetch on each login. Also fixed a React "setState in render" error from the login page's already-signed-in redirect.
- Test Runs list: "Passed"/"Failed" status filters matched nothing (sent PASSED/FAILED instead of PASS/FAIL).
- Perf harness `run-config.json` now records the S4 `ws` knobs (`CLIENTS`,
  `HOLD_MINUTES`, `RESULTS_PER_SEC`, `USERS`); previously omitted, so a kept
  `ws` run's provenance did not capture its client count, hold length, or
  probe rate.
- Perf harness measurement-validity fixes (external Codex review): per-op
  `count>0` thresholds everywhere a duration threshold exists (a tag-scoped
  p95 over zero samples evaluates to 0 and passes — the gate could pass an op
  it never exercised); the S4 probe starts after a 10 s subscribe-settle
  window so late handshakes are not misattributed as fan-out loss; gate
  baselines are stamped with CPU/cores/RAM/arch instead of CPU model alone
  (baseline re-measured, capturing the delta-payload write-path gain:
  add-result baseline 4.3 → 1.3 ms); `analyze.sh` uses exact nearest-rank
  p95 and survives midnight rollover; the perfseed caveat in `perf/README.md`
  now matches the implemented hard-link/parent-symlink guards.
- Run detail page crashed on load ("Something went wrong") since the effect
  dependency-array lint cleanup: the mount effect read `loadRun` /
  `loadCurrentAnalyses` from its dependency array before their `const`
  declarations (TDZ `ReferenceError`). Declarations now precede the effect.
- Read-path query scaling on large databases (S3 finding, ~1M results): the
  runs list computed status and defect-type counts in two passes, and the
  defect pass's `status IN ('FAIL','ERROR')` predicate baited SQLite into
  scanning the whole table via the status index (~2s per page); both counts
  now come from one grouped query pinned to the `test_run_id` index.
  Analytics summary/trend/flaky-candidate queries are now answered entirely
  from a new covering index `run_results(start_time, status, test_case_id)`
  instead of fetching every wide row in the date window, and the flaky
  detector's per-test-case history reads are index-only ordered scans on
  `run_results(test_case_id, start_time, status)` (names are resolved only
  for the returned page). Superseded single-column/duplicate indexes on
  `run_results` are dropped at startup (`test_case_id` ×2, `start_time`, and
  the old `(test_case_id, status, start_time)` composite), so ingest writes
  fewer index entries than before. At the large perf tier this takes
  `GET /api/runs` from ~2.1s p95 to ~35ms, `/api/analytics/summary` from
  ~740ms to ~50ms, and `/api/analytics/trend` / `flaky` from ~2.3–2.4s to
  ~220–300ms.

### Added
- Performance test harness (phase 1): a `perf/` k6 suite for the result-ingest
  write path — smoke check plus the S1 "CI ingest storm" capacity scenario —
  and a `perfseed` CLI that provisions scratch databases with a deterministic
  dataset, perf users, and write-scoped API tokens. The CLI refuses to touch any
  non-`perf-*.db` database (or a symlinked one) and writes its token manifest at
  mode 0600. Load pipelines send `test_name_snapshot` and spread across a
  `TOKENS`-sized (default 100) token pool so the measured write path matches
  real clients rather than harness artifacts.
- Perf harness hardening (post-review): the runner refuses a busy port and ties
  the readiness probe to the server it started (a stale listener can no longer
  be measured as the current build); the server is a direct child with the
  cleanup trap installed first, so teardown genuinely waits for graceful
  shutdown; capacity targets treat k6's threshold-failure exit (99) as the
  expected mapping-run outcome while `smoke` still hard-fails; `RESULTS_PER_RUN`
  is validated in the init context (a typo aborts the run instead of producing
  a vacuously green summary); scenarios assert `tokens ≥ peak VUs` at init and
  rate mode's new `MAX_VUS` knob defaults to the token-pool size, with an
  observational `dropped_iterations` threshold; `perfseed` additionally refuses
  hard links, symlinked parent directories, and a symlinked manifest path; the
  seed manifest now carries `{id,name}` pairs so k6 no longer re-derives the
  seeded case-name format (reseed with `RESEED=1` after upgrading); the k6 lib
  loads the manifest via `SharedArray` and pre-serializes result payloads to
  cut load-generator overhead; seeding is owned by a single `perf/scripts/seed.sh`
  used by both `make seed` and the runner's auto-reseed.
- Perf run provenance: every results directory now gets a `run-config.json`
  recording git SHA (+dirty flag), k6/Go versions, machine specs, and all knob
  values (`null` = scenario default), replacing the "record these manually"
  instruction; rate-mode runs append `-rate` to the results directory name so
  closed- and open-loop `ingest-storm` results stay distinguishable.
- Perf phase 2 (read paths): `medium` (~100k results) and `large` (~1M)
  seeder tiers; S2 `mixed` scenario (browsing reads with an ingest storm
  joining at half-time — the read-latency delta is the finding); S3 `dataset`
  scenario (fixed read mix per tier for a dataset-scaling curve); a weighted
  read-mix k6 lib driving runs list/detail, analytics, and FTS search with
  per-op thresholds; `perf/scripts/analyze.sh` for windowed per-op
  p95/error tables from server logs; shared k6 config (`perf/k6/config/`)
  for thresholds and workload profiles; the seed manifest carries
  `historical_run_ids`; the runner reseeds automatically when the manifest
  and target tier DB disagree; the seeder rejects non-positive counts and
  results not divisible by runs.
- Perf phase 4: S6 regression gate — `make -C perf gate` runs a fixed 3-minute
  mixed profile against a freshly-seeded small tier and fails if any
  operation's p95 exceeds its committed, machine-stamped baseline
  (`perf/baselines/gate-<tier>.json`, refreshed via `make -C perf
  gate-baseline`) by more than 30 %; all perf scenarios moved from the
  deprecated `--summary-export` to a shared `handleSummary` (vendored
  k6-summary keeps the terminal output; `summary.json` now uses the
  handleSummary shape with values under `.values`).
- Perf phase 3: S4 WebSocket fan-out scenario (`make -C perf ws`) — session-
  cookie authenticated clients (Bearer tokens cannot open WS connections)
  subscribe to `runs:*` while a paced probe posts results; measures broadcast
  lag from server timestamps, count-based delivery loss, and behavior at the
  1000-global/20-per-user connection caps. The seed manifest now carries the
  perf users' shared password, and `seed.sh` exposes a `USERS` knob.
- **Webhook signing-secret rotation.** `POST /api/webhooks/{id}/rotate-secret` generates
  a new HMAC signing secret and invalidates the old one; a matching action in Settings →
  Webhooks lets you rotate a secret from the UI. The signing secret is also now revealed

### Upgrade notes
- **Non-root container, existing deployments:** the backend now runs as uid 1000. If your
  `db_data` volume was created by an older, root-run container, it's root-owned and the
